# Compose 应用部署规范

本规范适用于本仓库 `docker-compose/` 下新增和调整的应用。优先遵循应用上游要求和现有服务的实际运行方式；确需例外时，在应用目录的 README 中说明原因。不要为了统一格式而改变已有服务的运行行为。

## 目录与职责

- 每个应用或一组紧密关联的服务放在 `docker-compose/<应用名>/`，目录名使用小写和连字符；新文件优先命名为 `docker-compose.yaml`。
- Compose 文件描述镜像、网络、挂载、非敏感参数和服务关系。属于同一应用、需要一起管理的组件放在同一份 Compose 文件中。
- 需要持久保存的真实环境变量放在宿主机 `/etc/configs/<应用名>/.env`；其他需要手动维护的应用配置优先放在 `/etc/configs/<应用名>/`。
- 可在应用目录提供 `.env.example` 和 README，记录所需变量、配置位置、启动方式与依赖；示例不得包含真实密码、令牌或密钥。实际 `.env` 不提交 Git。
- 数据库数据、应用生成的数据和缓存优先使用命名卷；如果上游要求绑定目录或有明确运维需要，可使用宿主机目录并说明。

## 环境变量与密钥

在 Compose 中用绝对路径引用实际环境文件：

```yaml
services:
  app:
    env_file:
      - /etc/configs/app/.env
```

- 密码、令牌、API 密钥等放在受保护的配置文件中，不写入 Compose、示例、README 或日志。合理设置文件及目录权限；例如 root 运行的服务可以使用 `root:root`、文件 `600`。实际权限需满足运行 Compose 的用户及容器的读取需求。
- 无敏感信息的端口、时区和功能开关可直接写在 Compose 的 `environment` 或其他对应字段中；需要集中维护时也可放在 `.env`。同名变量在 `environment` 中的设置会覆盖 `env_file` 中的设置，应避免无意覆盖。
- `env_file` 用于设置容器环境，不等于为 Compose 文件中的 `${VAR}` 插值提供变量。若需要通过环境文件控制端口、镜像等 Compose 字段，明确记录当前 Compose 实现支持的加载方式和完整启动命令，并验证加载结果；避免输出包含密钥的完整解析配置。也可以直接在 Compose 中写明非敏感值。
- 检查 Git 忽略规则是否覆盖真实环境文件；迁移现有配置前核对引用、权限和内容一致性，避免泄露或覆盖已有配置。

## 网络与基础服务

- 优先复用现有的 PostgreSQL、Redis、RabbitMQ 等 base 服务，按实际需要申请数据库、账号或连接配置，不为每个应用重复部署一套基础设施。
- 网络模式按服务需求选择。base 服务通常使用 host 网络；应用可按需使用 bridge、端口映射或 host 网络。只开放需要的端口，并确认是否需要绑定到本机地址。
- 容器访问宿主机服务时，根据实际 Podman 网络和应用配置确认访问地址；外部已有服务的可用性需要单独检查，Compose 内的 `depends_on` 不管理外部服务。

## 运行与验证

- 使用 Podman 和当前环境可用的 `podman-compose` 管理，检查镜像来源、版本、端口、容器名称和持久化路径；根据服务实际需要设置重启策略、健康检查和日志限制。不要假设 `always` 与 `unless-stopped` 在 Podman 中的开机行为完全相同，应结合实际启动机制验证。
- 创建前阅读上游文档和本仓库相邻服务的配置；涉及共享基础设施时核实连接方式、权限和依赖启动顺序。
- 部署前用对应的 `podman-compose ... config` 检查配置是否可解析；该命令可能输出密钥，禁止将完整输出写入日志或聊天。
- 需要实际部署时，检查容器状态、日志和适当的健康接口，并验证关键依赖及持久化位置。只有完成对应检查后才能声称服务可用。
- 已有运行中服务的配置修改、重建或重启，先确认操作范围并获得用户授权；变更前保留可恢复的原配置。避免无关服务受到影响。

## 新应用检查清单

1. 确认上游部署要求、现有基础服务、端口及持久化位置。
2. 在应用目录编写 Compose，并在 `/etc/configs/<应用名>/` 准备受保护的真实配置；需要时提供无密钥的示例和 README。
3. 区分 Compose 插值与容器 `env_file`，检查变量优先级和 Git 忽略规则。
4. 按部署范围解析配置并完成运行验证；记录配置路径、依赖和必要的启动方式。
